# The units were written for a systemd DOB does not have

**2026-08-12/13, station DOB.** Every unit in `services/agent/systemd/` was
written against the systemd on this laptop. DOB is Ubuntu 16.04 and runs
**systemd 229**, released 2016. Two of the units could not work there, and one
of them would have failed at the worst possible moment.

```bash
systemctl --version | head -1
```

```
systemd 229
```

That command is now the first step of any station bring-up. It costs nothing
and it is the only thing that would have caught either bug before the fact.

---

## 1. Why this is not a normal compatibility problem

systemd treats two kinds of "too new" completely differently, and the
difference decides whether you find out in a minute or in a month.

**An unknown *key* is a warning.** The unit loads. It starts. It fails later,
somewhere that looks like a broken script.

**An unknown *value* or *prefix* can be fatal.** The unit does not load at all,
and the failure names the parse error, not the version.

So the two failures below look nothing alike, and only one of them points at
its own cause.

---

## 2. `chirp-drop-watch` — the silent kind

Installed, enabled, started:

```
Job for chirp-drop-watch.service failed because the control process exited with error code.
Process: 19996 ExecStart=/home/ionouser/ionograms-handler/tools/drop-watch.sh (code=exited, status=1/FAILURE)
```

Exit 1 from a shell script under `set -eu` reads as a bug in the script. It was
not. The unit had:

```ini
StateDirectory=chirp-drop-watch
```

`StateDirectory=` arrived in **systemd 235**. On 229 it is an unrecognised key:
a line in the journal, and nothing else. `/var/lib/chirp-drop-watch` was never
created, never chowned, and the script — running as `User=ionouser` — died on
`mkdir` in a root-owned directory. Every visible symptom pointed at the script.

The pre-235 idiom is `PermissionsStartOnly=true`, which runs the `ExecStartPre`
lines as root and `ExecStart` as `User=`:

```ini
PermissionsStartOnly=true
ExecStartPre=/bin/mkdir -p /var/lib/chirp-drop-watch
ExecStartPre=/bin/chown ionouser:ionouser /var/lib/chirp-drop-watch
```

`ProtectSystem=strict` went the same way — the *key* is old, the **value**
`strict` needs 232. `full` is the pre-232 equivalent that still protects `/usr`,
`/boot` and `/etc`, and leaves `/var` writable, which this unit needs anyway.
`RestrictSUIDSGID` (242) and `LockPersonality` (235) were dropped: they were
belt-and-braces on a unit that already runs `NoNewPrivileges=true` with
`ProtectHome=read-only`.

## 3. `chirp-rx.service` — the kind that costs a drive to Dombås

The recorder unit contained, from the day it was written:

```ini
ExecStartPre=+/sbin/ethtool -G enp0s25 rx 4096
```

The `+` prefix — "run this one as root even though `User=` is set" — needs
**systemd 231**. On 229 there is no such prefix, so systemd reads the whole
token as a path. `+/sbin/ethtool` is not absolute. **The unit fails to load and
the recorder never starts.**

Take that in sequence. The migration from `dombas.sh` to systemd begins by
stopping `dombas.sh`, which means stopping the radio; then
`systemctl start chirp.target`; then the recorder does not come up, and the
error is about a path rather than a version. The station is off air while
someone reads systemd changelogs.

It never surfaced because **nothing has ever installed these units at DOB** —
acquisition there is still `dombas.sh`. The bug was latent for as long as the
file has existed, and would have surfaced exactly once, in the one situation
with no margin. Same fix as above:

```ini
PermissionsStartOnly=true
ExecStartPre=/sbin/ethtool -G enp0s25 rx 4096
ExecStartPre=/sbin/sysctl -w net.core.rmem_max=500000000
ExecStartPre=/bin/mkdir -p /dev/shm/hf25
```

`PermissionsStartOnly` is per-unit, not per-line — coarser than `+`, which is
why newer systemd replaced it. Here it applies to three pre-steps that all want
root anyway.

## 4. What stops it happening again

`tests/test_systemd_units.py` pins the whole directory to the station's actual
version:

```python
MIN_SYSTEMD = 229
```

Four checks, one parametrised over every `.service`, `.timer` and `.target`:

| check | catches |
|---|---|
| no directive newer than `MIN_SYSTEMD` | the `StateDirectory` class — the silent one |
| no *value* newer than it | `ProtectSystem=strict` on 229 |
| exec paths absolute, prefixes supported | the `+` class — the fatal one |
| `User=` plus a root-only `ExecStartPre` implies `PermissionsStartOnly` | the half-fix: dropping `+` for compatibility and forgetting what it did |

The fourth exists because it is the natural mistake to make while fixing the
third, and it reproduces the drop-watch failure exactly.

Two things about the test that are easy to get wrong:

- **Comments are skipped when scanning for directives.** These unit files
  discuss directive names constantly — this document's whole subject is which
  directive is too new — so a naive line scan flags its own explanation.
- **The version maps are not exhaustive and do not need to be.** They cover
  what these units actually reach for. A directive absent from `INTRODUCED` is
  assumed old enough; add entries as new ones are used.

All four were verified by breaking a unit and watching the test fail, not by
watching a green run. A version-floor test that has never failed is
indistinguishable from one that scans nothing.

**Raise `MIN_SYSTEMD` when a station is upgraded, and not before.** The number
is not a preference — it is the oldest host these files must run on, and
lowering the bar in the test lowers nothing on the station.

## 5. The general shape

Both bugs are the same shape as the packet-loss work in
`docs/2026-08-11-recorder-packet-loss.md`: **a thing believed to be in place,
never checked, and checked only because something adjacent broke.** The units
had been written, reviewed and committed; what had never happened was one
`systemctl --version` against the machine they were for.

The station is Ubuntu 16.04, which reached end of standard support in 2021.
Nothing here argues for upgrading it — an acquisition host that works is worth
more than a modern one that needs revalidating — but it does mean every
platform assumption in this repo is about nine years out of date by default,
and the ones that matter should be pinned by a test rather than remembered.
