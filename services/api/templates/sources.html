identify this emitter

Nothing in a detection says who is transmitting. The name you give here is a judgement, made the way cyprus1 was resolved to NIC — and it is load-bearing: it is written into the schedule as transmit_name, which calc_ionograms.py puts in the product's file name and in txname. This pipeline reads that back as the transmitter's identity and looks up its coordinates and band ceiling by it. An emitter you cannot name can still be scheduled — call it what you know it as — but that string is what every product from it will be called.

Letters, digits, underscore and dot — no dash. The product file name is dash-delimited (lfm_ionogram-{tx}-{rx}-{ch}-{id}-{t0}.h5), so a dash inside the code does not fail to parse, it shifts every field after it.

slots to sound:

One entry per ticked slot. Each is another sounding per cycle competing for the ringbuffer window — see the README on reading find_timings.log before ticking many.

verified transmitters

Identified once, kept with the census row that settled it. These are what a schedule is composed from — a raw census row cannot be scheduled, because it has no name and no id, and calc_ionograms.py reads both without a default. Choosing which of them to sound, and starting the sounding, is on the console, beside the station that would do it: the schedule and the recorder are one decision, and this page has to read the archive before it can render at all.
